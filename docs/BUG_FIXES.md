## BUG-001：收件箱操作后未移出

2026-10-05 后续规则调整：用户明确要求整理状态单选，当前互斥规则以 BUG-005 为准；下方保留当时修复证据。

- 报告日期：2026-10-05；来源：用户实际测试。
- 现象与复现：在收件箱选择一条内容，标记已读、稍后处理或归档；内容仍留在收件箱，也能在已读等筛选下找到。
- 预期：收件箱只包含未处理内容，任意一项处理状态为真就移出；全部更新保留所有内容，各状态筛选仍可查看对应内容。
- 原因：默认 quick=all，未对收件箱限定处理状态；未处理查询没有排除 deferred；各筛选页标题固定为“收件箱”，导航计数使用全部内容总数。
- 修复范围：统一未处理查询与计数、默认及返回收件箱的筛选、筛选标题和导航高亮；保留现有三项独立状态与用户数据。
- 验证（2026-10-05）：`npm test` 全部 14 项通过，真实 Core/SQLite 检查确认已读、稍后处理、归档任一状态都会排除收件箱，叠加状态需全部撤销才会返回；全部更新的记录总数保持不变。
- 桌面验证：`SUBSCRIBE_FLOW_VERIFY_OUTPUT=/tmp/subscribe-flow-bug-001-verification npm run smoke:renderer` 通过。使用真实 Electron/Preload/Python 和隔离 SQLite 的 25 条样本，覆盖详情、卡片菜单、撤销、批量归档、筛选标题、侧栏计数、同一路由返回收件箱、清除搜索及末页清空后返回首页。处理后收件箱 20 条、已读 1 条、已归档 4 条，全部更新仍为 25 条；Core 重启后收件箱正确，页面重载后处理状态持久化。
- 截图：[处理后的收件箱](verification/bug-001-inbox-after-processing.png)。已检查布局与计数；截图中的采集提示来自离线验收环境。本轮未重新验证平台采集，未修改用户正式数据库。
- 提交：`048f2da`（`fix(inbox): remove processed notes from the pending inbox`）。

## BUG-002：悬浮提示未及时取消

- 发现日期：2026-10-05；来源：合并 feature/enhancements-minimax 前审查。
- 现象与复现：鼠标进入图标按钮后，在 260ms 内移到无提示区域；延迟到期后仍出现原按钮的提示。
- 预期：移出按钮应取消待显示的提示。
- 原因：提示还未显示时 anchor=null；鼠标移到普通区域得到 t=null，t===anchor 导致提前返回，未清除延迟计时器。
- 修复范围：只有存在目标且等于当前锚点时跳过；无目标时清理提示与计时器。
- 验证：修复前真实 Electron 复现快速划过后仍弹提示；修复后通过快速划过、正常悬停、禁用按钮、键盘焦点事件、Esc、滚动、单浮层复用及危险按钮标记检查。另有 14 项 Node 测试通过。验证脚本使用隔离会话与 DOM 事件，不访问用户数据。
- 提交：`deb6fa6`（`fix(desktop): cancel tooltip delay when pointer leaves its target`）；与 Minimax 增强 `225204d` 一并快进合并到 `main`。

## BUG-003：同一毫秒的任务顺序不确定

- 发现日期：2026-10-05；来源：M6 恢复流程审查。
- 现象与复现：在相同毫秒时间戳下先创建 ID 较大的任务，再创建 ID 较小的任务；最近任务查询把先创建者放在前面，恢复时也可能选择旧任务。
- 预期：创建时间相同时仍按实际插入顺序显示并恢复最新任务。
- 原因：原查询的次排序字段是随机 UUID。
- 修复：任务列表和调度恢复查询使用 SQLite rowid 作为创建时间相同时的次排序。
- 验证（2026-10-05）：`test_same_millisecond_jobs_use_insertion_order_instead_of_random_ids` 固定相同时间戳并使用反向 ID，通过真实 SQLite 验证后来插入的任务优先。52 项 Python 全量测试通过。
- 提交：`2f67d5c`（`feat(scheduling): add opt-in automatic refresh and durable recovery`）。

## BUG-004：恢复回溯占用全部自动调度名额

- 发现日期：2026-10-05；来源：M6 新实现审查，尚未交付版本中的问题。
- 现象与复现：中断的历史回溯自动恢复后，另一个订阅已到期；调度器等整个回溯结束后才创建它的刷新任务。
- 预期：历史回溯每页释放共享资源，其他来源的到期检查能在分页间执行。
- 原因：自动任务并发判断把恢复中的回溯也当作唯一的刷新任务。
- 修复：保留一个到期刷新名额，最多同时挂起一个恢复回溯和一个定时刷新；实际平台请求仍按共享资源串行。
- 验证（2026-10-05）：`test_backfill_yields_shared_resource_to_due_subscription` 阻住恢复回溯第一页，将另一来源设为到期；释放后验证该来源在回溯末页之前执行。52 项 Python、16 项 Node 与正式 Electron Renderer 离线回归通过。
- 提交：`2f67d5c`（`feat(scheduling): add opt-in automatic refresh and durable recovery`）。

## BUG-010：验收复用旧任务而误报新请求失败

- 发现日期：2026-10-05；用户要求再次复现“登录问题”时发现。
- 复现：首次匿名采集进入 waiting；之后登录并再次执行真实验收脚本。sync.start 按产品合并规则返回 created=false 和旧 job_id，脚本直接读取旧 -352 并称为本次失败。
- 预期：真实复验必须明确创建/重试新任务，检查 job_id 与创建时间；已有执行任务不可冒充本次请求。结果必须保留 coverage 和条目错误，不能把有限窗口成功称为全历史，也不能把条目错误称为登录失败。
- 原因：脚本没有检查 created、job_id 或任务时间，错误输出还缺少页数和条目错误证据。另有打包验收连接定位只匹配无 hash 的 URL，无法识别已恢复的 #/channels 页面。
- 修复：增加 startFreshJob，等待任务显式重试（类型不符则取消后按本次参数启动），拒绝复用已有执行任务；输出新任务 ID/创建与更新时间。输出 mode/pageBudget/coverage/itemErrors/error；仅 succeeded 且无任务/条目错误才能通过，有效窗口仍不等于全历史。页面定位兼容 hash 路由。
- 验证：真实 Core 回归复现旧 waiting 任务跨重启被合并，修正后创建新 ID 并确实产生第二次采集；补充有限窗口成功、部分完成及条目错误证据检查。实际打包界面经 hash 路由读取并重试得到新任务，10 页 / 193 条入库。
- 状态：已修复。最终 20 项 Node 全量通过；hash 路由下实际打包界面连接与读取已通过。提交 `5036159`。所有先前受影响结论同步更正，旧证据明确标为非新请求。

## BUG-012：打包升级验收的旧库样本与版本号不一致
