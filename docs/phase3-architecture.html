标准模型在哪里？

在 Adapter → Gateway → Core 的返回链路上。ContentItem 是数据对象，Repository 才是存储入口。

订阅路径用 FetchPage 携带内容；人工路径先返回 ContentReference 查重，再读取内容。

两个业务入口，共用同一套渠道与内容库

“人工添加”与“订阅的手动刷新”是不同动作；手动刷新仍属于订阅采集。

订阅采集

手动刷新、历史回溯、定时自动检查

  1. 建立真实来源与订阅

    SubscriptionService 经 Gateway 解析来源；用户确认后保存订阅。

  2. 发起同步任务

    用户操作或 Scheduler 调用 SyncService，使用任务预算与故障阻塞规则。

  3. 读取平台列表

    ChannelGateway → Adapter.fetch_page()，Adapter 返回含 ContentItem 的 FetchPage。

  4. 按稳定身份原子入库

    Repository 查重；新内容、首次收录事件、页进度／检查点在对应事务内保存。

  5. 返回采集结果与变更事件

    页面局部更新，后台任务消费持久事件；重复内容保留原记录。

intake_method = subscription
日历依据：原始发布时间

人工添加

粘贴单条链接、查看预览、确认保存

  1. 识别链接对应的渠道

    IntakeService → Gateway.route_item_url()，使用 Adapter 声明的单篇能力。

  2. 解析标准身份，先查重

    Adapter.resolve_item() 返回 ContentReference；已存在则直接返回原记录。

  3. 读取单篇并生成预览

    Adapter.read_item() 返回标准内容；预览本身不创建内容、订阅或同步任务。

  4. 用户确认后再次查重

    Repository.save_manual() 在事务中保存，防止预览期间自动采集已经先入库。

  5. 返回保存结果与变更事件

    首次保存记录手动添加时间；不自动订阅该作者，也不制造同步任务。

intake_method = manual
日历依据：首次保存成功的添加时间

共同的内容身份与首次收录规则

channel + namespace + external_id 相同即为同一内容。两种路径使用相同仓储查重；首次成功收录决定原有方式和时间，重复操作保留已存正文及用户整理记录。

两种方式均保存真实原始发布时间。正文是否存在由 body_state 表达，不由“手动／自动”或平台名称推断。

内容保存后的 AI 通路

持久事件／任务 → 自动打标用户触发 → 总结草稿偏好与内容任务 → 智能优先级→AiGateway→协议 Adapter + HttpTransport

总结先返回可编辑草稿，由用户保存进笔记。自动打标和智能优先级分别维护任务与版本，不由渠道 Adapter 决定。

内部实现 A / 来源解析与列表

WxrankService → WxrankTransport

resolve_source · fetch_page

第三方付费 API。账号解析、列表分页、调用账本、缓存、限流与续采由内部服务处理；读取列表信息与原文链接。

付费配置只影响这些操作。

内部实现 B / 单篇文章

BrowserBridge → WechatSession

match_item_url · resolve_item · read_item

通过 Main 的 wechat-api.mjs 读取并解析官方文章页面，确认公众号与文章身份、正文和原始发布时间。

人工添加无需付费密钥，不创建订阅。

两种实现返回同一套业务身份，交回同一 Gateway 与 Core：

Source　wechat:account:{规范 biz}ContentItem　wechat:article:{规范 biz}_{mid}_{idx}

完整正文标 body_state=full；仅列表信息标 list_only。

wxrank 保留为供应商配置、密钥与费用记录名称；它不再注册成渠道 Adapter 或出现在平台筛选中。持久 biz ↔ gh_id 绑定独立保存，清资料缓存后仍能定位已订阅公众号。

公共描述符的 backend 用于连接与路由；实际访问协议由 Adapter 内部实现决定。源码中的 B站 OpenCLI 适配器为历史／非桌面替代实现，不与正式桌面 B站适配器同时注册。
