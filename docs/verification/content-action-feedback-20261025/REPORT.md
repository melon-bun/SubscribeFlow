# 优先级／归档：即时反馈与智能开启条件复验

2026-10-25，Codex 直接实施。用户进一步反馈「加入智能优先级后变卡」，要求点击响应低于 0.1 秒，并明确偏好先播放动画、后续操作在后台完成。结论：实际开启智能判断的隔离副本中，全部八个操作的首帧反馈低于 100ms；保存失败回退、统计正确性和阅读位置通过验收。

## 定位

1. 前一轮性能报告关闭了副本的智能判断，未覆盖用户实际开启条件；本次 `priority.status.enabled=true`，原始证据单列，不把两轮当成完全同条件的严格 A/B。
2. 加入智能优先级后，最终优先级表达式多了智能结果／策略／连接版本有效性判断。旧侧栏取数仍用九次 content.list 和逐平台 content.list；反复扫描与 DTO 读取放大了成本。
3. 原来所有 content.changed（包括归档／已读／稍后）都会进入一次判断资格检查。这些处理状态并非模型输入或人工偏好信号。
4. 真实复现阅读跳动：智能开启时，从自动改成人工会移除「重新判断」按钮。通用滚动协调器错误地把正文下方标签当列表锚点，导致 detail.scrollTop 从 120 变为 92。修复后保持 120，正文节点也保留。

## 实施

- 控件本地预览与持久内容分开。点击立即更改按钮选中态并启动原有滑块动画，显示「正在保存…」；不提前改写内容缓存、最终优先级来源或侧栏计数。
- 保存和查询异步继续，控件锁仍防止同一条内容被重复提交；成功后按 Core 回执落定，失败清除预览、取消残留动画、恢复原控件并提示。初始／解锁阶段只更新按钮属性，不重建文章和列表。
- 新增 Main 内部使用的 content.stats：一次分组查询返回九项全库计数与平台计数，沿用同一个 EFFECTIVE_PRIORITY 表达式，不抓正文。并行的 getCounts/listPlatforms 共享在途快照；查询完成即释放，不留过期计数缓存。
- content.changed 附字段元数据，仅处理状态变动时优先级服务跳过资格检查；人工改档、恢复自动、标签与其他内容变更照常处理。
- 阅读区域不使用标签作为列表锚点，并关闭浏览器自动锚定与手动位置恢复的竞争；未改变列表／看板／标签页的锚定规则。

## 测量：首帧反馈与后台完成分开记录

正式 Electron + Renderer + Main + Core，SQLite 只读备份到临时目录，保留智能开启；凭据文件和用户会话未复制，测试不调用真实模型。数据写入、故障注入均只发生在副本。没有改动日常库／配置／凭据／会话。

previewMs 是观察到按钮预览后实际 requestAnimationFrame 首帧的时间；writeMs 是实际写入回执时间；settledMs 包含计数、活动列表和控件解锁。后台用时受负载／合并通知影响，**不宣称全部保存和统计在 100ms 内完成**。这是当前设备样本，不能保证任意设备负载下的固定时限。

| 操作 | 首帧反馈 ms | 写入回执 ms | 全部刷新完成 ms | 观测后台调用数 |
|---|---:|---:|---:|---:|
| priority-high | 11.0 | 17.6 | 313.0 | 8 |
| priority-medium | 10.7 | 14.7 | 352.1 | 8 |
| priority-low | 11.2 | 204.5 | 1280.3 | 13 |
| archive | 73.1 | 8.3 | 547.1 | 9 |
| archive-from-inbox | 10.5 | 101.2 | 703.5 | 9 |
| priority-leaves-filter | 12.0 | 20.4 | 638.2 | 9 |
| manual-before-restore-auto | 9.4 | 14.4 | 455.4 | 8 |
| restore-auto | 38.3 | 8.4 | 321.2 | 8 |

全部首帧为 9.4～73.1ms。典型操作 8～9 次后台调用，额外内容通知合并的一条为 13 次，全部整块内容区重建为 0 次。额外事件会继续处理，未为了减少数字丢弃变更。

另将一次保存人为挂起：首帧 4.4ms，实际检测到动画已运行且数据库值仍未改变；随后注入失败，控件恢复原值并重新可用。这证明反馈不等待后端成功，也没有把预览当成持久化成功。
