# 优先级／归档操作性能修复（Codex）

2026-10-25。用户反馈点击优先级、归档时卡顿，明确要求 Codex 直接优化。已修复，日常数据未改动。

## 原因与改动

保存本身通常只需几十毫秒，但原 saveContent 在写入前、回执后、全部刷新结束时都用 renderContent() 重建整个内容区，销毁列表、详情及阅读节点。保存后 refreshData(true) 还会重读连接、调度、任务、标签目录等无关数据；内容事件又排一轮重复读取，按钮持续等待整套刷新结束。

- 单条优先级／处理状态及同类批量操作仅刷新 content。侧栏计数与列表仍从 Core 读取，不在界面猜统计结果。
- 强制局部刷新消费同类已排队事件，其他类型的通知仍留在队列，不丢失标签／渠道等变更。
- 写入相关回显使用现有 reconcileWithScroll，保留列表、详情正文节点；优先级控件来源和禁用状态仍按权威回执更新。
- 同一内容仍串行写入，等待活动列表重新读取后才解除操作锁，保留归档离开列表、优先级离开筛选、分页补位等正确性。
- 总览复用的详情弹窗也改用同一个局部协调方法。未改数据存储、标签统计或模型调用。

## 实测

正式 Electron + Renderer + Main + Core，通过 SQLite 只读连接备份用户数据库到临时目录。在副本上关闭智能判断、实际点击并核对持久化结果，结束删除副本；日常数据库／配置／凭据／会话未修改。无网络或真实模型调用。before/after JSON 仅含耗时、RPC 方法名与计数，不含内容标题正文或密钥。

单位为毫秒，settled 为实际点击到操作锁解除（包含列表刷新）。这是单机复测样本，后台负载会影响时间；不是跨设备性能保证。

| 操作 | 修改前 | 修改后 | 后台调用数 | 整块内容区重建次数 |
|---|---:|---:|---:|---:|
| priority-high | 964 | 196 | 45 → 21 | 3 → 0 |
| priority-medium | 744 | 187 | 45 → 21 | 3 → 0 |
| priority-low | 702 | 184 | 45 → 21 | 3 → 0 |
| archive | 428 | 202 | 46 → 22 | 3 → 0 |
| archive-from-inbox | 653 | 217 | 46 → 22 | 3 → 0 |

三档优先级中位数由约 744ms 降至 187ms。优先级不改变筛选成员时，列表卡片／详情／正文节点全部保留；归档或改档导致内容离开当前筛选时按实际列表正确切到下一条。切换到另一篇正文较多的内容仍需要构建新详情，追加的「改档离开高优先级筛选」样本为约 506ms，如实保留在 after.json。

- `npm run smoke:renderer`：完整正式链路通过，包含写入锁、刷新排空、下一次写入持久化、批量/页末、列表与总览、弹窗详情、优先级来源与统计、重启持久化。
- `npm run smoke:refresh:views`：三个视图刷新探针通过；既有旧桩缺 getPriorityStatus 的日志仍只记，不扩展修复范围。正式 Renderer 的 priorityBridgeSmoke 通过。
